# 第一阶段：Qt 开发环境搭建（最难的一步，全是坑）

## 1. 绕开 Qt 官方账号

**问题**：Qt 官方图形安装包要求登录 Qt 账号，账号未完成邮箱验证，装不了。

**怎么做**：改用 `aqtinstall`（Another Qt Installer）——第三方 Python 命令行工具，直接从 Qt 官方镜像下载预编译包，不需要账号：

```powershell
py -m pip install aqtinstall
py -m aqt install-qt windows desktop 6.8.3 win64_mingw
```

**为什么**：aqt 本质就是替你下载 Qt 官方编译好的二进制文件，和图形安装包装出来的东西完全一样，只是跳过了账号界面。

**学到的方法**：官方工具走不通时，先找它有没有命令行/无界面的等价物，往往限制只加在 GUI 上。

## 2. 镜像选择（踩了三遍坑）

| 镜像 | 结果 |
|---|---|
| 官方源 | 慢 |
| 清华 tuna | qtdeclarative.7z 校验和损坏，装到一半报错 |
| 阿里云 mirrors.aliyun.com/qt | 成功，最稳 |

只装一个模块时加 `--archives qtmultimedia` 只下载模块本体（约 24MB），不连带下载几 GB 无关组件。

**方法**：大文件下载失败时换镜像，不要重试同一个源；能精确指定包就不要全量下载。

## 3. 装 MinGW 编译器和 Qt Creator

- MinGW 13.1.0：`C:\Qt\Tools\mingw1310_64\`（g++/gdb/mingw32-make 都在 bin 里）
- Qt Creator：

```powershell
py -m aqt install-tool windows desktop tools_qtcreator qt.tools.qtcreator -O C:\Qt -b https://mirrors.aliyun.com/qt
```

- **关键坑**：aqt 默认装到「当前命令行所在目录」！装错过一次，后来用 `robocopy /E` 合并进正确目录再删掉误建目录。

**方法**：命令行工具先搞清楚它的默认输出目录（aqt 是 `-O` 参数），别盲目回车。

## 4. 在 Qt Creator 里注册 Kit

Qt Creator 装完不认识编译器和 Qt 版本，要用自带命令行工具 `sdktool` 注册：编译器 → 调试器 → Qt Version → Kit 四步。

两个血坑：
1. **MinGW 编译器类型必须选 `ToolChain.Mingw`**，不能选通用 GCC——否则 Qt Creator 调用 `make` 而不是 `mingw32-make`，构建失败。
2. **sdktool 必须加 `-s <用户配置目录>`**，否则配置写进全局目录，Qt Creator 读不到。

**方法**：GUI 软件的配置一般落在 `%APPDATA%` 下，工具链注册本质就是往那里写 JSON/ini。

## 5. 两条最重要的环境结论（后来反复用到）

- **MinGW 的 Qt 库只有 Release 版**（没有 Qt6Cored.dll）→ 只能构建 Release，不能混用带 `d` 的 Debug DLL。
- 系统没装 CDB 调试器 → Qt Creator 里不能断点调试，但编译运行不受影响。
- 项目保留两条构建链：`gui.pro`（qmake，日常用）和 `CMakeLists.txt`（VS 生成器），互不干扰。

# 第二阶段：空白窗口 → 棋盘棋子

## 6. MainWindow 初始化为干净模板

把 Qt Creator 生成的 MainWindow 砍到只剩 `setupUi`，给 board.cpp 补 `#include <algorithm>`。

**为什么**：MinGW 对「间接包含」比 MSVC 严格——MSVC 里用 `std::sort` 不写 `<algorithm>` 也能过（别的头文件碰巧带了），MinGW 直接编译报错。跨编译器代码要显式包含你用到的每个标准库。

## 7. 手绘棋盘（核心思想：单一数据源）

全部用 QPainter 代码绘制：木纹渐变、双线外框、楚河汉界、九宫斜线、炮位/兵位小直角。

**最关键的架构决策**——三个函数作为唯一几何数据源：

```cpp
Geo makeGeo(QSize)          // 窗口尺寸 → 格距、原点
QPointF crossPt(g, r, c)    // 棋盘坐标 → 像素
bool hitCross(g, pos, r, c) // 像素 → 棋盘坐标
```

绘制棋子、画提示点、判断鼠标点中哪个交叉点，全部走这三个函数。

**为什么**：绘制用一套公式、鼠标命中用另一套公式，窗口缩放时两套必然漂移错位。一个数据源 = 永远对齐。这是整个项目最重要的工程思想。

## 8. 棋子立体感

径向渐变（亮部偏移做高光）+ 双层描边 + 投影 + 楷体字（红方「帅仕相」，黑方「将士象」）。

## 9. 走法提示点

点击棋子后，直接调用引擎已有的 `generateAllMoves` 生成全部合法走法，筛出属于当前棋子的：空位画绿点、有敌子画红圈。

**为什么好**：没有为 UI 重写任何规则，引擎说能走就能走——UI 层复用逻辑层，绝不复制规则代码，规则改一处全对。

# 第三阶段：对局功能补齐

## 10. 将军呼吸动画

QTimer 每 80ms 触发，相位 `m_animPhase += 0.18`，用 `qSin(相位)` 算红圈半径/透明度，将帅周围呈呼吸效果。

**为什么不用多线程**：动画是 UI 的事，QTimer 由事件循环驱动，足够流畅；多线程刷新控件反而要跨线程通信。

## 11. 胜负判定 + 杀法名弹窗

`checkGameOver` 返回 0 进行中 / 1 将死 / 2 困毙（象棋特有：无子可动也算输），配 `getKillTypeName` 显示杀法名。

## 12. 悔棋的数据结构

```cpp
struct Step { Move move; int piece; int captured; bool byRed; };
```

每步记录：谁从哪走到哪、被吃的是什么。悔棋一次撤两手（AI + 玩家），棋子归位、被吃子放回。

**为什么**：撤销操作的本质是「保存足够的现场」。只记坐标不够（被吃的子没了无法恢复），必须存 `captured`。写任何操作前先想「我将来要怎么撤销它」。

## 13. 重新开局

重置棋盘、历史、选中状态，并复位将军边沿标志（见第 22 条）。

# 第五阶段：AI 思考「变长」——界面假死排查

## 15. 现象 → 假设 → 定位

AI 每手搜索 10 秒，而搜索在 **UI 线程同步执行**——这 10 秒窗口不响应、不重绘，看起来像卡死/变慢。

## 16. 解法：后台线程 + 棋盘副本

```cpp
class AiThread : public QThread {
    int m_board[10][9];  // 启动前从主线程拷贝
    void run() { m_result = getAIMove(m_board, ...); }
};
```

启动时把棋盘**按值拷贝**进线程，AI 在副本上搜，主线程界面流畅；搜完发 `finished` 信号（队列连接，自动切回主线程）落子，`deleteLater` 回收。

**为什么敢不加锁**：先确认了引擎搜索函数**零全局棋盘依赖**（只认传入的数组参数），两份棋盘互不干扰。

**要学走的**：
1. 耗时计算绝不能放 UI 线程；
2. 多线程共享数据的第一选择不是加锁，而是能不能给每个线程一份副本（无共享 → 无锁 → 无 bug）；
3. 跨线程回 UI 用信号槽，不要直接操作控件。

顺带加了难度下拉（笨糖果10秒/一般15秒/聪明20秒，引擎里 `setAiTimeLimitMs`）和状态栏思考计时器。

# 第六阶段：两次「崩溃」排查课

## 17. 改难度后崩溃：空指针

加难度选项时删掉了 `m_levelCombo = new QComboBox(central);`，后面却调用 `m_levelCombo->addItem(...)`，对空指针调方法 → 启动崩。

**怎么定位**：带调试信息重新构建，用 gdb 批处理脚本抓崩溃栈（`gdb -batch -x dbg.gdb`，用脚本文件绕开 PowerShell 引号转义问题），栈直接指向 `QComboBox::addItem(this=0x0)`。

**教训**：**编译通过 ≠ 运行没问题**。编译器只检查语法和类型，不检查「这个指针有没有 new 过」。Qt 控件必须先 new 出实例再调方法。

## 18. setCurrentIndex(1) 改 0「又崩了」

实测代码是对的——崩的是**旧 exe**：改完源码没重新编译，运行的还是上一个有问题的版本。

**教训**：
- 改 C++ 必须重新构建（Qt Creator 的 Ctrl+R 会先编译再运行；编译失败时可能直接运行旧 exe 迷惑你）。
- `setCurrentIndex(n)` 合法范围 0~项数-1，越界 Qt 静默忽略。

**通用方法**：排查「改了没效果」先怀疑构建产物是不是旧的——确认你跑的二进制确实包含你的改动。

# 第七阶段：音效系统

## 19. 先讲完整步骤，批准后才动手

方案：Qt Multimedia 模块 → WAV 文件 → qrc 资源嵌入 → QSoundEffect 播放。

## 20. 安装 qtmultimedia（又踩镜像坑）

- 模块名不叫 `multimedia`，叫 **`qtmultimedia`**（用 `aqt list-qt --modules` 查到——不知道名字就查，别猜）。
- 清华源损坏重演，阿里云用 `--archives qtmultimedia` 只抓本体成功。

## 21. 用 Python 标准库合成音效

用 `wave` + `math` 合成 6 个音（select/move/capture/check/win/lose）：不同频率正弦波 + 包络（淡入淡出防爆音），22050Hz 单声道 16bit PCM。

**为什么这个格式**：QSoundEffect 对低延迟短音效最稳的格式是无压缩 PCM WAV；单声道 22050Hz 体积小、播放开销低。

## 22. 三个播放层面的关键设计

1. **qrc 嵌入**：wav 编进 exe，不依赖外部路径，拷给别人不丢素材。
2. **构造函数预加载**：启动就 `new QSoundEffect + setSource`，否则第一声因异步加载哑火。
3. **将军音效「边沿触发」**：

```cpp
if (m_redInCheck && !m_wasRedInCheck) playCheck();
m_wasRedInCheck = m_redInCheck;
```

只在「没被将军→被将军」的跳变瞬间响一声，否则每帧重绘都重播，连成噪音。持续状态要响一声，用边沿触发，不要用电平触发。

## 23. 部署多媒体插件

windeployqt 必须带上 `plugins/multimedia/`（ffmpegmediaplugin.dll + windowsmediaplugin.dll）和 Qt6Multimedia.dll，否则独立运行时**静音但不报错**（插件找不到时 Qt 静默失败）。用 QT_LOGGING_RULES 打开插件日志验证 0 报错。

**教训**：Qt 插件缺失不报崩溃，只静默失效。功能「不工作但不报错」时，优先怀疑插件没部署。

# 第八阶段：用视频声音做双阵营音效

## 24. ffmpeg 提取 mp4 音频

```
ffmpeg -i 视频.mp4 -ar 22050 -ac 1 -sample_fmt s16 -t 3.0 out.wav
```

`-ar` 采样率、`-ac 1` 单声道、`-sample_fmt s16` 16位、`-t 3.0` 截前3秒。三个视频依次替换 capture/check/lose。

## 25. 红黑音效分离

原合成音备份成 `capture_red.wav / check_red.wav / lose_red.wav`。播放时判断阵营：AI 吃子放视频音，玩家吃子放原合成音；将军边沿、胜负音各归各。

**要点**：「局部替换」需求最安全的实现不是覆盖，而是**保留旧文件 + 新增文件 + 代码分支选择**，旧行为随时可回退。

## 26. 微信/QQ 找不到视频的插曲

WeChat Files、QQ NT 各目录只有缩略图，原视频已被清理，最后由用户直接上传解决。

**方法**：找不到素材时不硬找，让用户给最短路径。

# 第九阶段：电脑方伪 3D 虚拟形象（状态机实践）

## 27. 架构：一个状态机 + 一个 QLabel

```cpp
enum AvatarState { Idle, Thinking, Angry, Action, Lose, Win,
                   Selected, Good, Undo, Listening };
```

`setAvatar(状态)` 统一切换图片/动图和心情文字。
- 静态图：QLabel + QPixmap
- gif：QMovie（`label->setMovie(movie)`）
- 全部图编进 avatar.qrc

**为什么用状态机**：形象的脸只由「当前对局状态」决定，所有事件只调 `setAvatar`，不直接操作图片。入口唯一，不会两张脸打架。

## 28. 状态与触发

| 状态 | 触发 |
|---|---|
| Idle 待机 | 开局/取消选中 |
| Selected 观察 | 点选自己的棋子 |
| Thinking | AI 后台搜索期间 |
| Angry → Action | 玩家吃 AI 子：愤怒脸 0.8 秒 → gif 反击 1.3 秒 → 回思考 |
| Good 点赞 | 玩家走出将军（且没吃子），0.9 秒后转思考 |
| Undo 抱头 | 点悔棋时，配合确认弹窗 |
| Lose / Win | 玩家赢 / AI 赢 |
| Listening | 音乐开启时锁定 |

## 29. 时序序列用 QTimer 串

愤怒→gif→恢复用 `QTimer::singleShot(800, ...)` 串起来，不阻塞界面。

**边界处理**：序列进行中如果游戏结束/重开，旧定时器回调可能把脸改错——回调里要检查当前是否仍处于有效状态。异步定时器回调永远要假设「触发时世界已经变了」。

## 30. gif 拿不到（一堂加密课）

微信 4.x 的表情包 .dat、收藏库全是 AES 加密（连 SQLite 文件头都没有），密钥只在微信进程内存，本地无法离线解。最后把 gif 录成 mp4 发来，用 ffmpeg 转 gif。**绕不过加密就换通道。**

## 31. 悔棋确认弹窗 + 投降

- 悔棋：QMessageBox 问「是否要悔棋？」，选「是」才真撤，选「否」还原；AI 思考时禁用按钮。
- 投降：新增按钮，直接判负 → 大笑脸 + 播放第三段视频笑声 + 状态栏「你投降了」。复用已有判负/播放链路，不另写一套结局逻辑。

# 第十阶段：设置系统（背景/音乐/音量/先后手）

## 32. 背景切换

下拉选「经典木质/蓝发少女/魔龙降临」，绘制时把 QPixmap 画在棋盘底层。

**性能**：图片不能每次 paintEvent 都从 qrc 解码 JPEG——切背景时解码一次缓存成 QPixmap 成员，重绘只贴图。

## 33. 音乐播放（和短音效不同的技术）

长音乐用 **QMediaPlayer + QAudioOutput**（支持 mp3、循环、调音量），不用 QSoundEffect（为短音效设计，对压缩格式支持差）。

mp4 → mp3 用 ffmpeg 转换，编进 media.qrc。`setLoops(Infinite)` 循环，切歌先 stop 再换源。

## 34. 音量滑条

QSlider 0~100 → `audioOutput->setLinearVolume(v/100.0)`，实时生效。只控背景音乐；音效音量在各 QSoundEffect 上单独设定。

## 35. 先后手（坐标变换经典题）

选「后手（执黑）」时：
- 棋盘绘制旋转 180°（自己的黑子在下方）；
- 本质是在「逻辑坐标↔显示坐标」之间加一层 `(9-row, 8-col)` 翻转；
- AI 执红先行，状态栏、将军提示、胜负文案、音效归属全部跟随玩家实际执子方；
- AI 思考中禁止切换——任何会改变全局状态的设置，操作中途都要禁用。

## 36. 「听歌锁定」模式

音乐一响：形象锁定听歌脸、全部音效静音、表情不切换，只有关音乐恢复。

实现：在 `setAvatar` **入口加一道拦截**——`m_musicOn` 为真时任何状态都强制改成 `Listening`；同时 `setSfxMuted(true)`。关音乐解除拦截、恢复音效、回 Idle。

**思想**：「A 条件下忽略一切」的需求，在总入口拦截，不要在每个调用点加判断（会漏会忘）。

## 37. 全屏按钮（后来已删除）

`showFullScreen()` / `showNormal()` 切换。删除时把按钮、槽函数、成员变量一起清干净——删功能要删全套，不留死代码。

# 第十二阶段：自定义上传 + 性能优化

## 40. 用户自定义背景/音乐

下拉加「自定义…」，QFileDialog 选文件（图片 png/jpg/bmp/webp，音频 mp3/wav/flac/ogg/m4a）。

两个关键设计：
1. **复制到 exe 旁的 `assets/` 文件夹**，不引用原路径——用户删了原图程序里还能用。
2. **QSettings 持久化路径**：重启后自定义项还在。

已存在自定义文件时弹窗：直接使用 / 重新选择 / 删除 / 取消。删除时连文件带设置记录一起清，音乐还要先 stop 再删。

## 41. 性能优化（不降智力、不降体验，优先省时间）

### 优化一：走法生成重写（AI 变快核心）

- 旧做法：每个棋子遍历全盘 90 个交叉点，逐格调规则判断——大量检查注定不合法的格子。
- 新做法：按棋子类型直接枚举候选点：马测 8 个日字点、象测 4 个田字点、车/炮沿四条射线扫描遇障碍就停。候选从 90 降到个位数。
- **保证棋力不变的关键**：候选生成后，**仍过原来的 isValid* 规则函数 + 自将检查**，产出的合法走法集合完全一致。

**思想**：优化搜索空间而不是放松判断；先用便宜条件排除 90% 不可能项，再对剩下的做昂贵验证（粗筛→精排）。

# 贯穿始终的 10 条核心方法论

1. **单一数据源**：几何坐标、状态机入口（setAvatar）、规则判定都只准有一个出处，杜绝两套逻辑不一致。
2. **先测量/复现，再动手改**：崩溃用 gdb 抓栈、卡顿先定位在哪个线程、体积大先排序看文件。不凭想象修 bug。
3. **耗时操作离开 UI 线程**；跨线程优先传副本而不是加锁；回 UI 用信号槽。
4. **边沿触发，不要电平触发**：将军音、状态翻转类逻辑只在跳变瞬间动作。
5. **资源嵌入（qrc）+ 构造时预加载**：不丢素材、首操作无延迟。
6. **重复三次就脚本化/技能化**，并把踩过的坑写进注释。
7. **优化搜索空间，不放松正确性**：便宜条件粗筛 → 原标准精排；缓存解码结果；热路径避免堆分配。
8. **改完代码必须重新构建**；排查「没效果」先确认跑的是新二进制。
9. **发布思维 = 依赖闭包**：递归核对 DLL、模拟干净环境验证；源码包排除一切生成物。
10. **需求不清先问，删除操作先确认**。

# 第十五阶段：联机对战（2.1 → 3.1 主菜）

## 47. 最小可用协议：换行分帧的 TCP

`QTcpServer` 监听，`QTcpSocket` 连接，端口 = 30000 + 房间号。消息全部 UTF-8、以 `\n` 结尾分帧，三种消息：

```
MOVE 行1,列1,行2,列2   ← 对方走了一步
CHAT 文本              ← 房间聊天
AVTR 状态关键字        ← 3.1 新增：奶娃状态同步（见第 58 条）
```

`readyRead` 里把字节追加进缓冲区、按 `\n` 切开逐条处理；半条消息留在缓冲区等下次。**TCP 是字节流不是消息流**，分帧必须自己做。

**要点**：接收方**不校验走法**，直接 `executeMove`——发送方保证合法。双方棋盘各自维护，校验逻辑两边都写反而会出现"一边认一边不认"的分歧，不如约定发送方负责。

## 48. 房间号代替 IP：UDP 广播自动发现

让用户输 IP 太劝退。改成：创建房间时同时开一个 `QUdpSocket` 周期性广播「我是房间号 X，端口 P」；加入方在同网段广播地址（`255.255.255.255` + 各网卡定向广播）上收包，收到的房间列在列表里点一下就进。

- 房间号定死 4 位数字，TCP 端口按 `30000 + 房间号` 换算——号码即端口，不用协商。
- 广播包里带房间号，加入方按号码去连对应端口。

**为什么好使**：局域网广播不经过路由器、无需任何中心服务器，两台电脑连同一个 WiFi 就能互相看见。代价是只在同一网段有效——对家用场景足够。

## 49. 联机最容易翻车的是坐标系

走子消息里的「行列」必须双方口径一致：**第一个数是行（0-9，从上往下）、第二个数是列（0-8，从左往右）**。而执黑一方的屏幕是旋转 180° 渲染的，鼠标点出来的显示坐标要先翻转成逻辑坐标再发。规则：

- 消息里永远传**逻辑坐标**（以房主红方视角为基准）；
- 显示↔逻辑的转换只发生在本地输入和绘制两处（`displayPt`/`logicalPt`）。

**思想**：协议层用唯一坐标系，显示层各自转换；一旦把显示坐标发上网络，两边就永远对不齐。

## 50. 颜色与先手分配

房主执红先行，加入者执黑。代码里就一行：`m_playerRed = isHost`。别做"加入者选边"功能——每加一个自由度，状态同步的分支翻一倍。

# 第十六阶段：奶娃登场动画（解码器兼容性）

## 51. Windows Media Foundation 翻车

第一版用 QMediaPlayer 播 mp4。在部分机器上 `EndOfMedia` 立刻触发、画面一闪而过——MF 的解码通路异常时**不报错，只静默失败**（又一个"不工作但不报错"）。 

**解法**：改用「GIF 画面 + WAV 音乐」组合：`QMovie` 播动画、`QSoundEffect` 播音乐。两个都是 Qt 内建解码（gif 用 qgif 插件、wav 是 PCM），不碰系统解码器，任何机器表现一致。

**教训**：多媒体功能想"到处能跑"，选最笨的格式（GIF/WAV），别赌系统的解码器链路。

## 52. mp4 转高清 GIF 的两步法

直接 `-vf fps=15,scale=480:-1` 一条命令转 GIF，调色板只有 256 色且是全局估算，画面发灰。改两步：

```
ffmpeg -i in.mp4 -vf "fps=15,scale=480:480:flags=lanczos" -palettegen palette.png
ffmpeg -i in.mp4 -i palette.png -lavfi "fps=15,scale=480:480:flags=lanczos [x]; [x][1:v] paletteuse" out.gif
```

`palettegen/paletteuse` 按片源内容生成专属调色板，画质肉眼可见地好。音频另出一条 `pcm_s16le` WAV。

## 53. qrc 缓存陷阱

替换 qrc 里引用的 gif/wav 后重新构建，程序里还是旧的——因为 `qrc_videos.cpp` 是由 qrc 内容生成的中间文件，**改了素材不会触发它重新生成**。删掉影子构建目录里的 `qrc_*.cpp/.o` 再构建即好。

**通用**：「改了资源没生效」先怀疑生成物的缓存，不是代码问题。

## 54. 动画对话框的小讲究

- 「跳过 >>」按钮：动画再好看也不能绑架用户；
- 帧回调里检测 `frameNo >= total-1` 自动关闭，另加 9 秒兜底定时器防素材异常；
- 场景区 QLabel 尺寸必须和 GIF 完全一致（480×480）——比 GIF 大就露底色，设成黑色背景会出现一圈"黑边"（3.1 修复项）。**容器的背景色就是"素材之外"的观感，要么尺寸贴齐，要么配色和谐。**

# 第十七阶段：奶娃挂机（AI 代打）

## 55. 挂机按钮双态

召唤奶龙后出现「奶娃挂机」按钮；点击后 AI 替房主思考落子（约 3 秒一手），按钮变「停止挂机」。停止时**不等 AI 收尾，当前回合走完就交回手动**——中断一个正在进行的异步操作，最稳的时机是它的自然完成点。

## 56. 挂机 = 复用 AI 线程，不是新 AI

奶娃代打就是 `AiThread` 换个触发者：玩家点棋盘或定时器到期，殊途同归都调 `startAiThinking()`。挂机状态只决定「回合到我时自动触发」。**新功能先找它和老功能的公共通路，能复用就不新写。**

## 57. 吃子随机双音效/双动画

奶娃吃子时掷硬币：50% 新音效或原音效、50% 新动画或原打人动画，两个独立随机。素材全在 qrc 里，代码只是两个 `if`。**随机性是廉价的丰富感**，一个 rand() 让重复动作不腻。

# 第十八阶段：联机奶娃同步（AVTR 协议）

## 58. 两边都要有奶娃，但只有一个"真身"

奶娃的逻辑状态（思考/打人/点赞…）只存在于房主端，加入者端是纯"显示器"：

- 房主端：`setAvatar` / 吃子动画 / 召唤完成的入口处调 `syncAvatar(关键字)`，经网络发 `AVTR 关键字`；
- 加入者端：收 `AVTR` 就照着渲染 48px 的帮手条，本地 `setAvatar` 整体短路。

**门卫集中一处**：`syncAvatar` 开头判 `Online && isHost && 已召唤 && 网络在线`，不满足直接返回。所有调用点无脑调它，条件散落必然漏。

## 59. 状态全同步靠"入口广播"，不靠逐点通知

思考、愤怒、打人、点赞、悔棋、胜负……十几个状态如果每个交互点都写一句"发消息给对面"，必然漏改。实际只加了 3 处广播：`setAvatar`（覆盖全部常规状态）、吃子动画入口、召唤完成。**在状态的唯一出口广播，比在 N 个事件点各发各的可靠得多**——和"边沿触发在总入口拦截"是同一个思想。

## 60. 执黑渲染旋转决定 UI 摆位

加入者屏幕是旋转 180° 的：房主（红方）阵地在**屏幕上方**。所以加入者的"奶娃帮手"条要放在棋盘**上方**，看起来奶娃才像是站在房主那边帮忙。写联机 UI 前先问自己：对面屏幕上世界是颠倒的。

## 61. 对端掉线的清理

`onPeerDisconnected` 里把帮手条隐藏、锁操作。对面断线的瞬间，界面上属于"对方"的东西都要跟着消失，否则界面在说谎。

## 66. 单机模式：开局选难度+红黑方，对局中锁定不可改

**问题**：对局进行中，玩家可以随时改难度或切换红黑方，导致 AI 行为异常。

**改动**：
1. 新增 `refreshButtons()` 统一管理控件启用状态

3. 终局后解锁，可改设置后重新开局
4. 代码在 `MainWindow.cpp` 的 `refreshButtons()` 方法

**心得**：控件状态管理集中在 `refreshButtons()` 里，所有改变对局状态的地方（落子、终局、悔棋、重开）都调用它刷新，避免散落的 setEnabled 调用漏改。

**需求**：象棋规则中，长将（连续将军循环）或重复局面应判走子方输，防止无限将军和棋。

**改动**：

2. 利用已有的 Zobrist 哈希 + `pushGameHash()` 机制，每走一步后记录局面哈希

## 72. 内网穿透（cpolar）：局域网服务器公网可达

**需求**：互联网联机需要公网服务器，但服务器跑在本机 localhost。用 cpolar 做内网穿透，让外网能访问本机的 Node.js 服务。

**步骤**：
1. **发现 cpolar 已安装**：`C:\Program Files\cpolar\cpolar.exe` v3.3.18
2. **检查 authtoken**：`~/.cpolar/cpolar.yml` 已配置 authtoken 和 email
3. **分析已有隧道**：cpolar 配置了两个隧道——remoteDesktop(TCP 3389) 和 website(HTTP 8080)
4. **利用现有 website 隧道**：该隧道指向 localhost:8080，公网 URL 为 `https://67217a91.r22.cpolar.top`
5. **调整服务器端口**：将 Node.js 服务从 3000 改到 8080（`PORT=8080 node src/index.js`），匹配隧道
6. **更新 ServerConfig.h**：`defaultUrl()` 从 `http://localhost:3000` 改为 `https://67217a91.r22.cpolar.top`
7. **重新编译**：`mingw32-make -j4` 生成新的 gui.exe
8. **验证**：通过公网 URL 访问 `/api/auth/login` 返回 404（说明请求已到达服务器）

**架构**：
```
客户端 gui.exe
  → HTTPS REST/WSS → cpolar 公网 (67217a91.r22.cpolar.top)
  → cpolar 本地 → localhost:8080
  → Node.js 服务器 (HTTP + WebSocket)
```

**注意**：
- cpolar 免费版 URL 会变（每次重启隧道可能不同），本次用的是已有隧道的固定 URL
- cpolar 作为 Windows 服务运行，修改隧道配置需要管理员权限停启服务
- WebSocket 走 wss://（cpolar 自动 TLS 终止），客户端 `wsUrl()` 自动将 https→wss

**心得**：最初尝试 `cpolar http 3000` 新建隧道但失败（已有服务占用了 authtoken 会话）。转而利用已有的 website 隧道（指向 8080），把服务器端口改到 8080 就能直接用——比跟 Windows 服务权限斗争简单多了。

## 74. 对战邀请全局化 + 背景图铺满 + WS 可靠性修复（3.2 批次）

### 背景
用户反馈：① 邀请好友对战时，对方必须停在「互联网对战」页面才能看到邀请；② 邀请时好时坏收不到；③ 个人资料页背景图只能显示一小条，要求铺满。

### 74.1 邀请弹窗提升到 StartScreen 全局
- 之前邀请弹窗由 FriendsPanel（好友页）监听 inviteReceived，人不在好友页就没人接事件
- 现在挪到 StartScreen：onGlobalInvite → 存入 m_pendingInvites（QSet）→ 红点亮 → 立即弹 QMessageBox（父窗口用 QApplication::activeWindow()，任何页面都能弹）
- 关键坑：matchReady 也必须全局直连 StartScreen，否则在主菜单接受邀请后 match_ready 事件没人处理，进不了对局
- 「互联网对战」按钮新增红点（m_inviteBadge）：有未应答邀请时亮起，点击按钮重新弹邀请
- FriendsPanel 删掉邀请/匹配相关信号槽，避免双弹窗

### 74.2 「有时候收不到邀请」的三个叠加根因（全部实锤修复）
1. QWebSocket::close() 是异步优雅关闭：登出→再登录场景里 close() 后立刻 open()，socket 还在 ClosingState，新连接静默失败，WS 就此悄悄死掉，之后 sendEvent 里 if(!isOpen()) return 把邀请静默丢掉。→ 改用 abort()（立即复位到 Unconnected）
2. lambda + Qt::UniqueConnection 的 connect 直接失败：Qt 警告 "unique connections require a pointer to member function"，连接根本没建立——断线自动重连一直是坏的。→ 去掉 UniqueConnection（lambda 场景不适用）
3. 服务端待处理邀请断线不清理：pendingInvites 是纯内存 Map，A 邀请 B 后 B 客户端崩溃/退出，这条邀请永久残留，hasInvite/isBusy 把双方永久卡死（A 再邀请返回"邀请已发送，等待回应"，永不转发）。→ realtime.js 断线钩子里加 removeInvitesOf(userId)
- 另加 InternetClient::ensureOpenForSend()：用户主动发送（邀请/应答/私信/礼物）前检查连接，断了就提示"与服务器的连接已断开，正在重连"并顺手用缓存 token 重连——彻底消灭静默丢包

### 74.3 背景图铺满 + 上传前压缩
- ProfileDialog 改 paintEvent 把背景图铺满整个对话框（之前只是顶部横幅），叠白色半透明遮罩保证文字可读

### 75.1 所有模式回主菜单必崩的根因（gdb 栈实锤）
- 现象是残局返回菜单退出程序，实际**所有模式**返回都崩：gdb 栈 msvcrt!free ← handleClose ← QWindow::close

- 教训：**静态指针记录实例 + 栈对象 = 埋雷**，凡是会被"新一代实例"删除的窗口必须堆分配
